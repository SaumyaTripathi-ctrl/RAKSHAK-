# Rakshak record & crypto spec — v1

Normative. Implemented twice and kept byte-identical:

| Language | Location |
|---|---|
| Python (reference) | `backend/rakshak/codec/` |
| C (firmware) | `firmware/common/` (`rk_spec.h`, `rk_codec.h`, `rk_codec.c`) |

Shared test vectors: [`vectors.json`](vectors.json) (generated by `tools/gen_vectors.py`).
`backend/tests/test_codec.py` and `firmware/common/test/test_vectors.c` both check them; CI fails if the
two implementations ever disagree or the vectors are stale.

## 1. Conventions

* All multi-byte integers are **little-endian**. No padding, no alignment.
* `device_id`, `shipment_id`: ASCII `[A-Za-z0-9_-]`, 1–16 chars, NUL-padded to 16 bytes.
* Fixed-point instead of floats, so C and Python never disagree on formatting or rounding:
  `temp_x100` (°C×100, i16), `rh_x100` (%RH×100, u16), `ethylene_idx_x10` (0–1000 ⇒ 0.0–100.0 %, u16),
  `shock_g_x100` (u16), `lat_e6`/`lon_e6` (degrees×10⁶, i32).
* `seq` is a u32 **per device for the device's lifetime**. It is persisted in NVS *before* a record is
  encrypted and never reset (not per shipment, not on reboot). Firmware **refuses to encrypt** if the
  persisted `seq` cannot be read or written.
* `ts` is a u32 Unix epoch (UTC) when `ts_valid=1`; otherwise it is the device's monotonic
  seconds since its clock origin (see §6).

## 2. Record bodies

Every body starts with the same 42-byte common part:

| Off | Size | Field | Notes |
|---:|---:|---|---|
| 0 | 1 | `version` | 1 |
| 1 | 1 | `type` | 1 = TAG_SAMPLE, 2 = HUB_SAMPLE, 3 = EVENT |
| 2 | 16 | `device_id` | |
| 18 | 16 | `shipment_id` | |
| 34 | 4 | `seq` | u32 |
| 38 | 4 | `ts` | u32 |

### 2.1 TAG_SAMPLE (type 1) — **50 bytes**

| Off | Size | Field | Type |
|---:|---:|---|---|
| 42 | 2 | `temp_x100` | i16 |
| 44 | 2 | `rh_x100` | u16 |
| 46 | 2 | `ethylene_idx_x10` | u16 |
| 48 | 1 | `flags` | bit0 `LID_OPEN` (latched), bit1 `TS_VALID` |
| 49 | 1 | `batt_pct` | u8 |

### 2.2 HUB_SAMPLE (type 2) — **60 bytes**

| Off | Size | Field | Type |
|---:|---:|---|---|
| 42 | 2 | `temp_x100` | i16 (hub ambient) |
| 44 | 2 | `rh_x100` | u16 |
| 46 | 2 | `shock_g_x100` | u16 (max since previous sample) |
| 48 | 4 | `lat_e6` | i32 |
| 52 | 4 | `lon_e6` | i32 |
| 56 | 1 | `flags` | bit0 `LID_OPEN`, bit1 `TS_VALID`, bit2 `GPS_VALID`, bit3 `FAN_ON` |
| 57 | 1 | `flap_pct` | 0 / 25 / 50 / 100 |
| 58 | 1 | `batt_pct` | u8 |
| 59 | 1 | `alert_level` | 0 SAFE, 1 WARNING, 2 CRITICAL |

### 2.3 EVENT (type 3) — **50 bytes**

Same offsets as a tag sample; the three sensor fields are reinterpreted:

| Off | Size | Field |
|---:|---:|---|
| 42 | 2 | `event_code` (u16) |
| 44 | 2 | `arg0` (u16) |
| 46 | 2 | `arg1` (u16) |
| 48 | 1 | `flags` (same bits as a tag sample) |
| 49 | 1 | `batt_pct` |

| Code | Name | Meaning |
|---:|---|---|
| 1 | `TIME_SYNC` | `ts` = epoch at sync; `arg0 \| arg1<<16` = device monotonic seconds at that instant |
| 2 | `BOOT` | clock origin restarted (power loss/reset) |
| 3 | `LID_OPEN` | reed switch opened |
| 4 | `SHOCK` | `arg0` = shock_g_x100 |
| 5 | `LOW_BATTERY` | |
| 6 | `PAIRED` | tag bound to a hub/shipment |
| 7 | `KEY_ROTATED` | `arg0` = new `key_epoch` |

## 3. Hash chain

```
hash_0 = SHA-256( 0x00 × 32 || body_0 )          # genesis: prev_hash = 32 zero bytes
hash_n = SHA-256( hash_{n-1} || body_n )
```

One chain per device, covering all three record types of that device in `seq` order.
A hub forwards tag frames unchanged; the hub has its own chain.

Verification (backend, `rakshak.codec.chain`):

| Finding | Cause | Tamper? |
|---|---|---|
| `BAD_HASH` | stored `hash` ≠ SHA-256(`prev_hash` ‖ `body`) — body altered | yes |
| `CHAIN_BREAK` | `prev_hash` ≠ previous record's `hash` — edit + re-hash, or insertion | yes |
| `MISSING` | `seq` gap — deleted or not yet delivered | reported (may heal) |
| `DUPLICATE` | `seq` already held — QoS-1 redelivery (forgery if hash differs) | no / yes |

## 4. Keys

```
device_key = HKDF-SHA256( ikm = master_key (32 B), salt = none (32 zero bytes),
                          info = "rakshak-v1|<device_id>|<key_epoch>", L = 32 )
```

* `key_epoch` is a u16 stored in NVS with the key. Re-provisioning a device **increments** it, so a new
  key is used even though `seq` continues, and the epoch is in the frame header/AAD.
* The backend holds the master key (or per-device keys) and derives `device_key` from the unauthenticated
  header; a wrong epoch simply fails authentication.
* Devices hold only their own key, in an NVS partition under ESP32 flash encryption (see
  `docs/PROVISIONING.md`). **The ESP32 has no secure element**: a physically held device can, with
  effort, be made to give up its key. Flash encryption + secure boot raise the bar; they are not a
  hardware root of trust.

## 5. Frame (flash, BLE and MQTT payload)

```
frame  = header (24) || ciphertext (P) || gcm_tag (16)
header = version u8 | type u8 | device_id[16] | key_epoch u16 | seq u32      # also the GCM AAD
plain  = body || prev_hash (32) || hash (32)                                  # P = body_len + 64
nonce  = 0x00 × 8 || seq (u32 LE)                                             # 12 bytes
cipher = AES-256-GCM(device_key, nonce, aad = header, plain)
```

| Type | Body | Plaintext P | Frame |
|---|---:|---:|---:|
| TAG_SAMPLE | 50 | 114 | **154** |
| EVENT | 50 | 114 | **154** |
| HUB_SAMPLE | 60 | 124 | **164** |

The nonce is unique for a given key because `seq` is monotonic, persisted before use, and never reset;
a new key (`key_epoch`) is issued on re-provisioning. GCM authenticates the header, so `device_id`,
`key_epoch`, `seq` and `type` cannot be altered in transit.

After decryption the receiver additionally requires that the body's `version/type/device_id/seq`
equal the header's.

The header is deliberately unencrypted so a hub can ACK a tag's batch **by seq range without holding
any key**, and the backend can pick the right key.

## 6. Time

* The hub's GNSS time sets tag clocks over BLE **at pairing and on every batch ACK**.
* Until a tag has a valid time, it writes `ts_valid=0` and `ts` = monotonic seconds since its clock origin.
* A `TIME_SYNC` event carries `ts` = epoch and `arg32` = monotonic seconds at that instant. The backend
  re-bases every `ts_valid=0` record between the preceding `BOOT` event (or the first record) and the
  `TIME_SYNC`: `ts_est = ts_mono + (ts_epoch − mono_at_sync)`. Re-based times are flagged *estimated*
  in the API/UI.

## 7. Transport

* **BLE (tag → hub)**: request MTU ≥ 247; frames are batched into notifications; the hub ACKs by
  `(first_seq, last_seq)`; the tag deletes records only after the ACK. The ACK also carries current epoch
  time.
* **MQTT (hub → backend)**: topic `rakshak/{hub_id}/telemetry`, payload = exactly one frame (tag or hub),
  QoS 1, persistent session. `rakshak/{hub_id}/events` = JSON status/ACKs (not hash-chained).
  `rakshak/{hub_id}/cmd` = JSON commands (`FLAP_SET`, `FAN_ON`, `FAN_OFF`, `ALERT_*`, `ACK_*`).
  The backend dedupes by `(device_id, seq)`.
